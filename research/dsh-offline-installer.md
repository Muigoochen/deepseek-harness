# DeepSeek Harness 小白一键安装助手（设计讨论稿）

> 阶段：方案讨论。目标读者：让我和你都能看清「做给小白用的离线安装器」要长什么样、有多大、怎么实现。
> 结论以文档末尾「需要拍板的决策」为准，逐条确认后再进入实现。

## 1. 这个东西是做什么的

一个**带简单图形界面的 Windows 安装助手**：帮完全不懂编程的人，在一台新电脑上从零装好并打开 DeepSeek Harness 网页版，全程只点按钮、看提示，不看命令行。

它解决的核心矛盾是**下载太慢**：本项目要把近 1000 个依赖包从 npm 官方源慢慢拖（我们在本机已实测，仅 @openai/codex 单包就 140MB，几十 KiB/s 的速度非常痛苦）。这套方案让「慢下载」只发生**一次**（在我们这台机器上），之后所有电脑都直接用本地缓存，秒级安装。

同一套盘也服务自己：以后我换电脑 / 帮同事装，双击同一个安装器即可，不需重新研究流程。

## 3. 它在后台替你做的六件事

| 步骤 | 做什么 | 什么情况跳过 | 失败怎么处理 |
|---|---|---|---|
| ① 环境自检 | 查 Windows 位数、现有 Node/pnpm 版本 | — | 直接中文报错 |
| ② 装 Node.js | 没 Node 或版本旧 → 静默装随包带的 Node 24 LTS | 已有 22.19+/24+ | 提示用已下载的安装包手动装 |
| ③ 准备 pnpm | 用 corepack 启用；失败则用随包的 pnpm tgz 离线装 | 已有 pnpm | 给中文操作指引 |
| ④ 放好项目源码 | 把随包源码解压到用户目录（如 `%USERPROFILE%\deepseek-harness`） | 已存在且完整 | 警告是否覆盖 |
| ⑤ 离线装依赖（核心） | 在源码目录跑 `pnpm install --offline --store-dir <随包缓存> --frozen-lockfile`，**不联网** | 已有 node_modules | 提示「离线缓存不完整，请联网或换镜像补一次」 |
| ⑥ 构建 + 启动 | `pnpm run build`（第一次约 5–15 分钟）→ `pnpm dsh web` | build 产物已存在（`.dsh-build` 标记） | 中文报错 + 日志可复制反馈 |

第⑥步可能耗时几分钟，窗口内放进度信息和「完成后自动打开浏览器」的提示。

## 4. 为什么离线包是「依赖缓存」而不是「直接把 node_modules 打包」

这是本方案最该先想清楚的技术点：

- pnpm 的 `node_modules` 大量使用**硬链接/符号链接**来省空间。用 zip 打包分发，链接关系会碎：要么解压后体积爆炸（几十 GB），要么直接跑不起来。
- pnpm 自带**内容寻址缓存 store**：它只是一堆按内容哈希存放的文件，没有链接弱点，zip/7z 压缩解压后依然有效。
- 所以在打包机上把依赖完整下载一次 → 把 **store 目录打包** → 接收机用 `pnpm install --offline --store-dir 随包store` 安装，由 pnpm 自己在目标机重建正确的链接结构。这才是离线分发依赖的可靠姿势。

`pnpm store path` 能告诉你 store 在哪；本机现在已缓存约 995/1001 个包，只要把 `pnpm install` 完整跑通一次，store 就全了。

## 5. 随包内容清单与体积预估（诚实版）

| 内容 | 作用 | 估计体积 |
|---|---|---|
| 安装助手程序（installer.exe） | 图形界面 + 调度逻辑 | 10–30MB |
| `assets/node-24-LTS-x64.msi` | 离线装 Node（可选内置） | ~35MB |
| `assets/pnpm-11.7.0.tgz` | 离线装 pnpm | ~10MB |
| `assets/deepseek-harness-src.7z` | 官方源码快照（排除 .git/node_modules） | 50–200MB |
| `assets/pnpm-store.7z` | 依赖离线缓存（大头） | 未压缩 2–4GB；7z 后约 0.8–1.5GB，可分卷 |
| 合计 | | **约 1–2GB** |

给接收方的话术要点：网络再差也不怕，唯一要等的是自己机器的 build（几分钟）。

## 6. 技术选型（需要你拍板的第一件事）

| 方案 | 优点 | 缺点 | 适合 |
|---|---|---|---|
| **A. Python 3.11+ Tkinter，PyInstaller 打包 exe**（推荐） | 写 UI 逻辑快、依赖极轻、单文件分发；我可以用 subprocess 精确控制每一步命令与日志 | exe 可能被杀软报「未知发行者」；需要先在本机装 Python | 想快速做出可用的 MVP |
| B. C#/.NET WinForms/WPF | Windows 原生、UI 现代、可出签名包 | 开发链重（要 VS 或 dotnet SDK）；产出也上百 MB | 打算长期以 Windows 为主要平台 |
| C. 纯批处理/PowerShell 菜单 | 零依赖、最简单 | 不是「点按钮」的图形界面，不够小白 | 只是自己临时用 |

我建议 **A** 起步，后面想换 B 也不影响数据包结构（store 与源码通用）。

## 7. 硬性限制（关系到「给谁用」）

- **只能给 Windows 10/11 64 位**。代码/依赖里的原生二进制（codex、sharp、node-pty…）绑平台与 Node ABI；Mac/Linux 得另做数据包。
- **接收机需要装 Node 22.19+ 或 24+**——这正是步骤②要做的事（msi 静默安装需要管理员权限，界面会提前提示点【允许】）。
- 每台接收机**第一次**仍需本地 `pnpm run build`（5–15 分钟，不联网）。想连这步也省（二期）可以把「打包机的 build 产物」也做成离线增量包，但要求接收机平台/Node 与打包机一致，MVP 先不做。

## 8. 制作「离线安装盘」的产出物（打包机侧流程）

1. 在这台机器把 `pnpm install` 完整跑通（补全 store）。
2. 用官方方式确认能 `pnpm dsh web` 启动。
3. 打包脚本自动收集：源码快照（排除 .git/node_modules）＋ `pnpm store path` 的目录 ＋ pnpm tgz ＋可选 node msi。
4. 生成安装盘（一个大 7z/分卷包，或直接一个放好文件的目录结构，拷 U 盘/网盘均可）。
5. 在干净虚拟机里跑「一键完整安装」验证。

## 9. MVP 拆期（建议节奏）

- **阶段 0**：把 store 补全（本机 install 完整成功，含 codex 那几个大件）。
- **阶段 1**：最小核心（命令行阶段也接受）——检测 Node/pnpm → 离线装依赖 → build → 启动，先在第二台机器自验「不联网能跑」。
- **阶段 2**：图形界面（按钮、状态、中文日志、UAC 提示）。
- **阶段 3**：内置 node msi 静默安装、pnpm tgz 离线装、源码自动解压。
- **阶段 4**：打正式安装盘，干净虚拟机上全流程验收。
- **二期**：build 产物离线增量包；Mac/Linux 支持。

## 10. 需要拍板的决策（P0 优先级最高）

- **P0 技术栈**：A(Python+Tkinter) / B(C#/.NET) / C(批处理菜单)？
- **P0 接收对象**：对方的电脑都是 Windows 10/11 64 位吗？装没装过 Node？
- **P1 Node 安装包要不要内置**：内置=完全免下载但要打包 35MB 且需要管理员权限；不内置=提示对方先装 Node（对小白多一步）。
- **P1 数据包放哪**：整盘做成单个分卷 7z 传网盘/U 盘？还是先做一个本地目录版自己试？
- **P2 界面语言**：中文界面就够？（我按全中文设计）
- **P2 是否接受第一阶段先用命令行版自验**，UI 后补？

## 11. 文档不能替你决定的部分

- store 是不是真的够所有包离线装——只有在你把 `pnpm install` 完整跑成功后才能确认；届时 `pnpm install --offline` 全走的可能才成立。这是整个方案唯一的硬前提。
- 接收机跑 `pnpm run build` 需要能写硬盘空间（build 产物 + node_modules 合计可能再占 3–5GB）。
