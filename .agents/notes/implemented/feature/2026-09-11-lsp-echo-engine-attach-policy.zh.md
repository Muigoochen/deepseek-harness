# Agent Note: 一个项目一个引擎——lsp-echo 的 attach 策略

Status: implemented

[English](2026-09-11-lsp-echo-engine-attach-policy.md) | 中文

## Problem

lsp-echo 只在需要引擎时才决定由谁服务某个项目:检查发生时若编辑器不可连,它自起一个 headless Godot 引擎,而这个决定在该引擎存活期间一直有效。此后打开的 Godot 编辑器不会改变它。于是两个引擎同时服务一个项目——用户的编辑器带着它自己的一份文件系统扫描与语言服务器,我们的 headless 再带一份——直到 headless 引擎消失为止。循环里没有任何东西报告这件事:检查照常通过,只有机器在付代价。

它旁边还有两个较小的问题。桥把 host 状态记在自己的引擎目录内,于是同一个桥的两份副本(仓库检出与 profile 安装)读写不同的状态文件:`status` 会回答 `stopped: no live host`,而引擎其实正在跑——取决于问的是哪一份。另外,编辑器 attach 背后的信任模型——"编辑器端口上有活的对端,就是本项目的编辑器"——在编辑器打开的是**别的项目**时是错的:应答检查的语言服务器对这些文件一无所知,而空诊断会被读成干净通过。

## Decision

### 引擎决策按请求重做

持久桥客户端([`checkers/godot-lsp/godot-lsp.mjs`](../../../../plugins/lsp-echo/checkers/godot-lsp/godot-lsp.mjs) 的 `cmdClientd`)在服务每个请求之前都调用 `ensureHost`,而不只在启动时调用一次。端点变化会被跟随并重连:旧 socket 被丢弃时其 close 处理器不会退出进程,随后对着决定出的端点开一个新会话,该请求继续处理。冷启动行为不变——第一个检查到达时编辑器已在运行,仍然直接 attach 它。

### `attachPolicy` 决定编辑器后到时怎么办

引擎的机器配置里有 `attachPolicy`:

- `prefer-editor`(默认)——检查发现我们自己的 headless 引擎活着、而编辑器的端口也有应答时,把项目迁到编辑器上:停掉我们 spawn 的那个 headless 引擎,把编辑器记为引擎,并重连。一个项目,一个引擎。
- `cold-start`——谁先起就由谁继续服务。这是给"本机还跑着一个连编辑器 LSP 的编辑器插件客户端(VSCode 的 Godot 插件)"的机器用的,因为迁到编辑器会在单会话服务器上开一个新会话,把这个客户端挤掉一次。

`attachEditor: false` 的优先级高于两者:配置成纯 headless 的机器即使编辑器可达也保留自己的引擎,因此策略只在该开关允许的选项之间做选择。

迁移在既有的 host 启动锁下进行,因此两个桥进程无法同时停引擎并 attach,且它绝不触碰用户的编辑器进程。

### 服务别的项目的对端会被拒绝

LSP 握手之后,客户端检查对端在 `gdscript_client/changeWorkspace` 里声明的项目,而持久客户端在服务每个请求之前都会重做这项检查,因此晚于握手窗口到达的通知同样会被抓住。服务别的项目的对端被当作坏编辑器处理:该端口按与"编辑器无应答"路径相同的五分钟记录进黑名单,检查回退到我们自己的引擎。这条记录会在随后的状态重写中留存下来——无论是起我们自己的引擎,还是迁到某个编辑器上——因此被拒的端口在黑名单期内不会被再次探测。另一种做法——继续用这个对端——会把一个答非所问的结果变成假通过。

这次决定所迁移与重连的会话,正是[编辑器 LSP 会话 Note](../bug-fix/2026-09-11-lsp-echo-editor-lsp-single-session.zh.md)所记录的那一个。

### host 状态放在 DSH home 下

host 状态、host 日志与引擎自己那份诊断副本从 `<引擎>/.runtime/` 移到 `$DSH_HOME/lsp-echo-runtime/godot-lsp/`,与插件写的快照同处一个运行时根目录之下。旧位置保留为**读取**兜底,使升级后仍能复用已在运行的引擎;而每一次写入都会清掉旧副本,因此陈旧记录无法替活着的记录作答。桥的两份副本如今看到同一份状态。

## Alternatives considered

| 被否决 | 一句话理由 |
|---|---|
| 保留 cold-start 规则、只把它写进文档 | 只要编辑器在第一次检查之后打开,一个项目两个引擎就是常态,而循环无法报告它 |
| 用设置页按钮取代默认值 | 在有人注意到之前,资源代价一直留着;而策略本来就是个一行的配置改动 |
| 先探测编辑器端口上是否有活跃客户端,空闲时才迁 | 编辑器 LSP 是单会话的,任何能分辨"空闲"与"有人在用"的探测,都是那次会挤掉在用者的握手 |
| 在插件 host 半而非桥里做这个决定 | 该决定需要状态文件、编辑器探测与引擎进程的所有权——这些桥已经拥有 |
| 继续读写旧状态位置并在副本间同步 | 一个事实两个写入者;它的失败形态(`status` 从错误的文件作答)正是这次搬迁要消除的 |
| 把服务别的项目的编辑器当作可用、再过滤它的诊断 | 这里没有 TypeScript 那样的按文件过滤:对端答的是另一个项目,对本项目文件什么也没说 |

## Consequences

默认情况下一个项目由一个引擎服务,无论两者谁先启动,因此长期会话会在编辑器打开后收敛,而不再多养一个引擎。每次请求做一次决策的代价是读一次状态、加一次编辑器端口的 TCP 可达性检查;在编辑器应答之前它一直复用已启动的引擎。迁到编辑器会挤掉此刻连在该编辑器 LSP 上的其它客户端一次;`cold-start` 就是为"那个客户端很重要"的机器准备的、有据可查的退路。落到服务别的项目的编辑器上的检查,如今会切回我们自己的引擎,而不是默默通过。`status`、`stop` 与插件自己的工具链,无论由哪份桥副本执行,都对同一份状态文件作答。

## Testing

两个实验从一次性副本运行桥(它有自己的一份配置与旧状态目录),针对临时项目,并用 TCP 假监听充当引擎:

- 决策类:旧位置的 headless 记录 + 可达的编辑器 → 迁到编辑器、停掉 headless 进程、写入新状态并清掉旧文件;第二次调用复用编辑器且不再迁移;`attachPolicy=cold-start` 复用 headless 且让它继续跑;编辑器不可达时继续用 headless。
- 会话类:长期存活的 clientd 在 headless 引擎上启动并应答了一个请求,随后编辑器出现,下一个请求完成迁移、停掉 headless 引擎、重连并应答;后续请求不再发生切换,且丢弃旧 socket 没有退出进程。
- 错项目类:声明了另一个项目的编辑器被拒绝(黑名单消息),检查回退到我们自己的引擎。

实验为编写引擎而启动的 Godot 进程事后已终止,它们写下的运行时状态也已清除。
