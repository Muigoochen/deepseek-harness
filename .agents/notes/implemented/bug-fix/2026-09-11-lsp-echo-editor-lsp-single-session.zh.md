# Agent Note: 每个 Godot 编辑器 LSP 一个 lsp-echo 桥会话

Status: implemented

[English](2026-09-11-lsp-echo-editor-lsp-single-session.md) | 中文

## Problem

Godot 编辑器的语言服务器只接受一个客户端会话。第二个连接会记录 `Connection Taken` 并驱逐第一个，第一个随后丢掉所有在途请求。

`clientd` 的标识键包含角色，连同项目与 attach 端口一起，而 lsp-echo 以两种角色运行检查：每轮的常规检查与全项目基线扫描。面对已 attach 的编辑器，这两种角色各自持有到同一个单会话服务器的连接，于是后到者驱逐先到者，被驱逐角色的请求随即失败。症状不是错误答案——而是对确有诊断的文件返回空诊断，且时间点与基线扫描和会话首批编辑并发运行相吻合。

## Decision

[`lib/manager.js`](../../../../plugins/lsp-echo/lib/manager.js) 仅按项目与 attach 端口来标识 `clientd`。`role` 参数选择该进程发出哪种请求（常规扫描或全项目扫描）；它不是进程身份的一部分。一个已 attach 的编辑器恰好有一个桥会话，由插件内所有检查共享，Godot 引擎桥的重扫请求（[引擎桥 Note](../feature/2026-09-11-lsp-echo-godot-editor-bridge-rescan.zh.md)）也经由这同一个会话。

端口或 attach 覆盖值的变化仍会替换该项目的所有旧 `clientd`，因为先前进程的 host 决策已经针对旧端口运行过。

当 `clientd` 调用在传输层失败——超时、进程已退出或请求被取代——插件会先退役仍存活的 `clientd`，再退回一次性的 `check`，由后者开启自己的会话。若在那里留着旧进程，恢复期间就会有两个会话压在单会话服务器上，恰好让这次兜底所要救回的请求失败。带回引擎所报诊断的载荷意味着会话健康，予以保留。

## Alternatives considered

| 被否决 | 一句话理由 |
|---|---|
| 每角色保留一个 `clientd`，被驱逐后重连 | 两个会话面对单会话服务器时，驱逐就是常态；重连只会让每次基线扫描都踢掉下一轮检查 |
| 每次检查都新开会话，从不复用 | 每轮都要付会话启动开销，而编辑器 attach 模式存在的意义正是避免这一点 |
| 保留两个会话，用队列串行化角色 | 两个会话根本无法共存；串行化只能决定被驱逐的是哪一个 |
| 基线与检查重叠时退回 headless 引擎 | 丢掉 attach 的省算优势，并为编辑器已持有的信息再扫一遍项目 |

## Consequences

基线检查与常规检查共享一个编辑器会话，二者都无法驱逐对方，attach 路径保住了它的启动开销。传输层失败会替换会话，而不是与之竞争。

接受的代价：插件无法并发运行两个编辑器 attach 的检查——它们经由一个进程串行——且未来某个确实需要独立会话的角色必须显式要求，而不能从其名称继承隔离性。

## Testing

该失败可通过向同一个编辑器 LSP 会话附加第二个客户端复现；修复的验证方式是：对同一个已 attach 的编辑器跑一次基线扫描与一次常规检查，确认由单个桥进程服务二者，且第二次检查返回引擎的诊断而非空结果。
